# 修正 E2E 测试用例

读取 `e2e/tests/` 下已生成的 `.spec.ts` 文件，通过 MCP 浏览器重新分析页面，修复失效的选择器、错误的断言，或根据页面变化调整测试步骤。

**使用场景：**
- 页面 UI 改版后，旧的选择器失效
- 测试运行失败，需要排查并修复
- 需要补充遗漏的断言或交互步骤
- 页面功能变化，需要调整测试逻辑

---

## 工作流程

### 前置检查 1：检查项目是否在运行

**修正测试需要访问实际页面来验证和修复选择器，必须先确认项目已启动。**

1. 从环境变量 `BASE_URL` 获取项目地址，如果未设置则默认 `http://localhost:3000`
2. 使用 MCP `browser_navigate` 尝试访问 `BASE_URL`
3. 设置合理的超时判断（约 5-8 秒）

**如果项目未运行，立即主动向用户提问：**

```
⚠️ 无法访问项目（BASE_URL），项目似乎未在运行。

修正测试需要访问实际页面来验证选择器，请先启动项目后再重试。
（修正操作已取消）
```

终止流程，等待用户启动项目后重新执行。

### 前置检查 2：登录认证处理

在项目可访问的前提下，使用 MCP 浏览器导航到页面时，如果被重定向到登录页，**立即主动向用户提问**，要求提供测试账号。流程同 `/e2e-generate`。

### 阶段 1：定位待修正的文件

1. **扫描已有测试文件**：列出 `e2e/tests/` 下所有 `.spec.ts` 文件
2. **参数过滤**：如果用户指定了页面名或路由，匹配对应的 `.spec.ts` 文件（模糊匹配文件名）
3. **如果未指定参数且有多文件**：列出所有文件供用户选择
   ```
   请选择要修正的测试文件：

   1. login.spec.ts — 登录页
   2. user-profile.spec.ts — 个人中心
   3. product-list.spec.ts — 商品列表

   请输入编号，或重新执行时指定文件名：
   /e2e-fix login
   ```
4. **读取目标文件**：读取选中的 `.spec.ts` 文件内容，理解现有测试用例结构

### 阶段 2：分析页面与诊断问题

1. **导航到页面**：使用 `browser_navigate` 打开该页面的 URL（从测试代码中的 `page.goto()` 提取路由）
2. **获取页面快照**：使用 `browser_snapshot` 获取当前页面可访问性树
3. **逐一对比测试用例**，诊断以下问题：

   | 问题类型 | 诊断方法 |
   |---------|---------|
   | **选择器失效** | 测试中的定位器（`getByRole`、`getByText`、CSS 选择器）在页面快照中找不到匹配元素 |
   | **断言错误** | 预期的标题、文本、可见状态与实际页面不符 |
   | **交互路径变化** | 点击/填表等操作的顺序或目标元素发生变化 |
   | **元素缺失** | 测试依赖的元素（弹窗、列表项）在页面中不存在 |
   | **新增元素** | 页面上出现了测试未覆盖的新交互元素 |

4. **交互验证**：对可疑的选择器，用 MCP 工具实际执行操作来验证（点击、填表），确认是否能正常触发

### 阶段 3：生成修正方案并征得用户同意

**不要直接修改文件。** 先向用户报告诊断结果和修正方案：

```
🔍 login.spec.ts 诊断报告:

  ✅ test('页面加载正确') — 通过，无需修改
  ❌ test('成功登录') — 选择器失效
      问题: getByRole('button', { name: '提交' }) 不存在
      修正: → getByRole('button', { name: '登录' })
  ❌ test('登录失败提示') — 断言错误
      问题: 预期错误文本 "密码错误"，实际为 "用户名或密码错误"
      修正: → toHaveText('用户名或密码错误')
  ⚠️  检测到新元素 "忘记密码链接"，是否添加测试用例？

是否应用以上修正？(y/n)
```

- 用户确认后，执行修正
- 用户拒绝则跳过，继续诊断下一个问题

### 阶段 4：执行修正

1. **使用 `edit_file` 工具**，逐项修复诊断出的问题
   - 替换失效的选择器
   - 修正断言参数
   - 调整交互步骤顺序
   - 添加新的测试用例（如用户确认新增）

2. **如果用户要求新增测试用例**，参考 `e2e/plan.md` 中的用例名称（如有），或基于页面分析生成新的测试用例，命名格式与 plan 保持一致

3. **每次修正后记录变更**，最终汇总输出

### 阶段 5：输出结果

```
✅ 修正完成！

📋 login.spec.ts 变更汇总:
   ✅ test('成功登录') — 选择器已更新
   ✅ test('登录失败提示') — 断言已修正
   ✅ 新增 test('忘记密码链接跳转正确')

⚠️ 建议运行测试验证修正结果:
   /e2e-run login
```

---

## 注意事项

1. **不要重写整个文件**：只修正有问题的部分，保留其他无需修改的测试用例
2. **保留串行模式**：不要改动 `test.describe.configure({ mode: 'serial' })` 和 `beforeAll`/`afterAll` 结构
3. **不要改动 Page 共享逻辑**：保持 `let page: Page` 共享模式
4. **修正后建议运行测试**：提示用户执行 `/e2e-run` 验证修正效果
5. **如果页面变化较大**（路由变更、功能重构），告知用户可能需要重新生成，仅靠修正无法覆盖
6. **更新 plan.md**：如果新增了测试用例，同步更新 `e2e/plan.md` 添加对应条目（状态为 ✅）

## 示例

```
/e2e-automation:e2e-fix                        # 列出所有测试文件供选择
/e2e-automation:e2e-fix login                  # 修正 login.spec.ts
/e2e-automation:e2e-fix user-profile           # 修正 user-profile.spec.ts
/e2e-automation:e2e-fix /user/profile          # 也可用路由路径匹配
```
