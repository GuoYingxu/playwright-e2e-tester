# E2E 测试计划生成

扫描项目前端代码和文档，生成 E2E 测试计划 Markdown 文件 `e2e/plan.md`。
该文件是 `/e2e-generate` 的输入依据，包含每个页面的测试用例名称及其代码生成状态。
**纯静态分析，无需运行项目。**

**支持参数**：如果用户输入了页面名称或路由路径（如 `/e2e-plan 登录` 或 `/e2e-plan /user`），则只分析匹配的页面；留空则扫描所有页面。

---

## 工作流程

### 阶段 1：分析项目结构

1. 读取 `package.json` 了解项目技术栈
2. 扫描前端源代码目录，识别页面/路由文件：
   - **Vue 项目**：扫描 `src/views/`、`src/pages/`、`src/router/`、`/pages/`
   - **React 项目**：扫描 `src/pages/`、`src/routes/`、`app/`、`src/App.tsx`
   - **Next.js**：扫描 `app/` 目录（App Router）或 `pages/` 目录（Pages Router）
   - **Nuxt**：扫描 `pages/` 目录
   - **Angular**：扫描 `src/app/` 下的路由配置
   - **通用**：扫描 `src/router/`、`src/routes.ts`、`src/router.ts`
3. 读取路由配置文件理解 URL 路径与组件的对应关系
4. 如果项目有 README 或 API 文档，一并阅读以了解功能描述
5. **参数过滤**：如果用户指定了页面名称或路由参数，只保留匹配的页面（模糊匹配页面名/路由名）
6. 输出页面清单：列出所有待分析页面及其 URL 路径

### 阶段 2：分析页面功能（静态代码分析）

对每个识别出的页面，通过源代码分析来推断测试场景：

1. **读取页面组件源码**：找到页面路由对应的组件文件，分析其模板/JSX
2. **识别关键元素**（从代码中推断）：
   - 表单元素（`<input>`、`<form>`、`v-model`、`form` 等）
   - 按钮（`<button>`、`@click`、`onClick` 等）
   - 列表和表格（`<table>`、`v-for`、`.map()` 等）
   - 链接和导航（`<a>`、`router-link`、`Link` 等）
   - 模态框和弹窗（`modal`、`dialog`、`popup` 等）
3. **读取 API 相关代码**：识别页面调用的接口，理解数据交互逻辑
4. **读取项目文档**（README、API 文档等），补充功能理解
5. **根据代码分析推断测试场景**，为每个页面生成测试用例名称清单

### 阶段 3：生成 plan.md

输出 Markdown 格式的测试计划文件到 `e2e/plan.md`，结构如下：

```markdown
# E2E 测试计划

项目: <项目名称>
生成时间: <当前时间>
生成方式: /e2e-plan <参数>

## 页面清单

| # | 路由 | 页面名称 | 用例数 | 代码状态 |
|---|------|---------|--------|---------|
| 1 | /login | 登录页 | 3 | ❌ 未生成 |
| 2 | /user/profile | 个人中心 | 4 | ❌ 未生成 |

---

### /login — 登录页

| # | 测试用例 | 代码 |
|---|---------|------|
| 1 | 页面加载正确 - 显示登录表单 | ❌ |
| 2 | 成功登录 - 输入正确凭证跳转首页 | ❌ |
| 3 | 登录失败 - 错误密码显示错误信息 | ❌ |

---

### /user/profile — 个人中心

| # | 测试用例 | 代码 |
|---|---------|------|
| 1 | 页面加载正确 - 显示用户信息 | ❌ |
| 2 | 编辑个人信息 - 修改昵称成功 | ❌ |
| 3 | 上传头像 - 选择图片后预览 | ❌ |
| 4 | 修改密码 - 旧密码错误提示 | ❌ |
```

#### 格式要求

1. **页面清单表格**：顶部的汇总表，每页一行，状态列汇总该页所有用例是否都已生成
2. **每个页面的详情表格**：每个页面一个二级标题 `### /route — 页面名`，下接表格，每个测试用例一行
3. **状态标记**：
   - `❌` — 未生成代码
   - `✅` — 已生成代码
   - `🔄` — 部分生成（该页面部分用例已生成，部分未生成）
4. **备注列**：可在每页表格末尾添加备注说明（如 "依赖后端 API"、"需要登录态"）

#### 测试用例命名规范

每个页面至少包含以下场景（根据页面实际元素调整）：

- **页面加载**：验证页面标题、关键元素可见、接口返回
- **正向流程**：主要交互操作的成功路径（表单提价、列表查询、导航跳转）
- **反向流程**：错误输入、异常操作的反馈（空值、格式错误、无权限）
- **边界情况**：空数据展示、长文本、特殊字符
- **交互联动**：筛选条件组合、分页切换、Tab 切换

用例名称格式：`<操作场景> - <预期结果>`

### 阶段 4：输出结果

```
✅ E2E 测试计划已生成！

📋 共扫描 N 个页面，规划 N 个测试用例

📄 计划文件: e2e/plan.md

▶️ 下一步：使用 /e2e-automation:e2e-generate 根据计划生成测试代码
```

## 与 /e2e-generate 的协作

- `/e2e-plan` 生成/更新 `e2e/plan.md`，所有用例的代码状态初始为 `❌`
- `/e2e-generate` 读取 `e2e/plan.md`，按计划逐个生成代码
- 每次生成完成后，`/e2e-generate` **必须更新 `e2e/plan.md`**，将对应用例的 `❌` 改为 `✅`
- 用户可随时再次运行 `/e2e-plan` 重新扫描，保留已生成的 `✅` 状态（读取现有 plan.md 的生成状态并合并）
- 如果用户修改了 plan.md 手动添加用例，`/e2e-generate` 应识别新用例并生成

## 注意事項

1. 如果 `e2e/plan.md` 已存在，先读取现有文件，保留已有的 `✅` 状态标记
2. 新识别的页面和用例状态为 `❌`
3. 如果项目路由变化，已删除的页面从 plan 中移除，但需提示用户哪些页面被移除
4. plan 文件的 Markdown 格式必须严格一致，以便 `/e2e-generate` 可靠地解析
5. 如果指定了参数且没有匹配到任何页面，提示用户并展示可用页面列表

## 示例

```
/e2e-automation:e2e-plan             # 扫描所有页面生成计划
/e2e-automation:e2e-plan 登录        # 只分析"登录"相关页面
/e2e-automation:e2e-plan /user       # 只分析 /user 路由相关页面
/e2e-automation:e2e-plan 个人中心    # 只分析"个人中心"页面
```
